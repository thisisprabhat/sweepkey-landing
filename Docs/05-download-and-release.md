# 05 · Download and release

> Status: draft for review · 2026-10-27
> App repo: `/Users/prabhatkumar/Projects/utils/cleaner` (below: `cleaner/`). Site repo: `/Users/prabhatkumar/Projects/creations/websites/sweepKeyLanding` (below: `site/`).

This document is the path from source code to a visitor's Applications folder. It reuses the app repo's existing pipeline (`scripts/release.sh`, `.github/workflows/release.yml`, `scripts/configure-repo.sh`, `Casks/sweepkey.rb`) and adds one piece on the site side: the mirror sync script, which also writes the version used to build the download URL. Nothing in the app repo changes.

## Launch gate
**The site does not go live until the DMG is Developer-ID signed, notarized and stapled.** Today's `scripts/make-dmg.sh` DMG is ad-hoc signed, so Gatekeeper blocks it on every visitor's Mac. The gate is enforced in three places:
1. `scripts/release.sh` signs, notarizes and staples the app and the DMG, then runs `spctl` and `stapler validate` (it fails otherwise).
2. `site/scripts/sync-release.mjs` refuses any DMG that `spctl -a -t open --context context:primary-signature` rejects, so an un-notarized DMG can never reach the mirror or `release.json`.
3. The site build fails if `src/data/release.json` is missing, so the page cannot ship with placeholder version, size or checksum.

All three DMG URLs serve the same file, so one SHA-256 covers them.

## One-time setup

### 1. Apple Developer ID
1. Join the Apple Developer Program (individual or organisation).
2. In Certificates, Identifiers & Profiles, create a **Developer ID Application** certificate. Install it in the login keychain (Xcode → Settings → Accounts → Manage Certificates also works).
3. Note your **Team ID** (Membership details).
4. At appleid.apple.com, create an **app-specific password** for notarization.
5. Export the certificate with its private key as a `.p12` (Keychain Access → right-click → Export) with a strong password. This is for CI only; keep it out of every repo.

Check: `security find-identity -v -p codesigning` lists `Developer ID Application: <Name> (<TEAMID>)`.

### 2. Notary profile (local releases)
```sh
xcrun notarytool store-credentials sweepkey-notary \
  --apple-id "<apple-id-email>" --team-id "<TEAMID>" --password "<app-specific-password>"
```
`scripts/release.sh` uses the profile name from `NOTARY_PROFILE` (default `sweepkey-notary`). Credentials are never passed on the command line to the script itself.

Check: `xcrun notarytool history --keychain-profile sweepkey-notary` runs without an auth error.

### 3. GitHub repository
1. Create the public repo `thisisprabhat/sweepkey` on GitHub (web UI or `gh repo create thisisprabhat/sweepkey --public`), and push `main`.
2. In `cleaner/`, run:
   ```sh
   scripts/configure-repo.sh thisisprabhat
   ```
   It replaces `github.com/OWNER/` and `cask OWNER/` in every tracked file except itself. That covers `README.md`, `Casks/sweepkey.rb` (`url`, `homepage`) and `project.yml` (`SPARKLE_FEED_URL`). Owner must match `[A-Za-z0-9-]+`.
3. Check nothing is left: `git grep -n OWNER` should show only `scripts/configure-repo.sh` and the guard in `scripts/release.sh`. Commit and push.
4. Set the repo **About** website to `https://sweepkey.waygosquad.tech` and add topics (`macos`, `developer-tools`, `disk-cleaner`, `swift`).

`release.sh` refuses to run while `SPARKLE_FEED_URL` still contains `OWNER`, so this step cannot be skipped.

### 4. Sparkle keys
1. Get Sparkle's tools (`generate_keys`, `generate_appcast`) from the Sparkle 2.6.4 release tarball (the version the workflow pins) or from the resolved package in DerivedData.
2. Run `./bin/generate_keys`. It stores the private key in your login keychain and prints the **public** EdDSA key.
3. Export the private key for CI: `./bin/generate_keys -x sparkle-private.key`. Store it in a password manager, then delete the file.
4. **Never lose or rotate this key casually.** Every installed copy trusts only updates signed with it.

### 5. GitHub Actions secrets
Settings → Secrets and variables → Actions:

| Secret | Value |
|---|---|
| `DEVELOPER_ID_CERT_P12` | `base64 -i DeveloperID.p12 \| pbcopy` |
| `DEVELOPER_ID_CERT_PASSWORD` | The `.p12` export password |
| `APPLE_ID` | Apple ID email used for notarization |
| `APPLE_TEAM_ID` | Team ID |
| `APPLE_APP_PASSWORD` | App-specific password |
| `SPARKLE_PRIVATE_KEY` | Contents of `sparkle-private.key` |
| `SPARKLE_PUBLIC_KEY` | The public key from `generate_keys` |

### 6. No app-repo change for the download link
Decision (27 Oct 2026): all landing-page work stays in `sweepKeyLanding/`, so the app's `release.yml` is not changed. The site builds the versioned URL itself from `src/data/release.json` (written by `scripts/sync-release.mjs`):
`https://github.com/thisisprabhat/sweepkey/releases/download/v{ver}/Sweepkey-{ver}.dmg`.
A text link to `https://github.com/thisisprabhat/sweepkey/releases/latest` covers anyone who lands on the page after a newer release but before the site is redeployed.

### 7. Homebrew tap
1. Create the public repo `thisisprabhat/homebrew-tap`.
2. Copy `cleaner/Casks/sweepkey.rb` (after `configure-repo.sh`) to `homebrew-tap/Casks/sweepkey.rb`.
3. Fill in `version` and `sha256` from the first release (step 9).
4. Check: `brew tap thisisprabhat/tap && brew audit --cask --online --strict thisisprabhat/tap/sweepkey && brew style thisisprabhat/tap/sweepkey`.
5. Install test: `brew install --cask thisisprabhat/tap/sweepkey` → `Sweepkey.app` in `/Applications` and `sweepkey --version` prints `{ver}` (the cask's `binary` stanza links the CLI inside the app).

The cask declares `depends_on macos: ">= :tahoe"`, `auto_updates true` (Sparkle updates the app; `brew upgrade` skips it unless `--greedy`), `livecheck` via `github_latest`, and a `zap` stanza for `~/Library/Application Support/Sweepkey` and `~/Library/Preferences/com.prabhatkumar.Sweepkey.plist`.

## Each release

### 8. Build locally first (optional, recommended for 0.1.0)
```sh
cd cleaner
export APPLE_TEAM_ID=<TEAMID>
export SPARKLE_PUBLIC_KEY=<public-key>   # empty disables the updater in this build
scripts/release.sh 0.1.0 <build-number>
```
What it does, in order: CLI build + smoke test → archive with `MARKETING_VERSION` / `CURRENT_PROJECT_VERSION` → export with Developer ID → embed the CLI and its resource bundle → sign inside-out (Sparkle helpers, framework, CLI, app with entitlements; Hardened Runtime + timestamp) → notarize + staple the app → `spctl -a -t exec` → build, notarize, staple and validate the DMG → CLI zip.

Output in `cleaner/build/release/dist/`:
- `Sweepkey-0.1.0.dmg`
- `sweepkey-0.1.0-macos.zip`

Verify:
```sh
spctl -a -t open --context context:primary-signature -vv build/release/dist/Sweepkey-0.1.0.dmg
#   → accepted, source=Notarized Developer ID
xcrun stapler validate build/release/dist/Sweepkey-0.1.0.dmg
#   → The validate action worked!
```

**Build numbers:** Sparkle compares `CFBundleVersion`. CI uses `GITHUB_RUN_NUMBER`; a local run defaults to `git rev-list --count HEAD`. Do not mix the two for releases users receive, or a later CI build can have a *lower* build number and Sparkle will not offer it. Either always publish from CI (recommended), or always pass an explicit, increasing build number.

### 9. Publish through CI
```sh
git tag v0.1.0 && git push origin v0.1.0
```
`release.yml` runs on `macos-26`:
1. Imports the Developer ID certificate into a temporary keychain.
2. Stores notarytool credentials as profile `sweepkey-notary` in that keychain.
3. Runs `scripts/release.sh "${GITHUB_REF_NAME#v}" "$GITHUB_RUN_NUMBER" build/release`.
4. Generates `appcast.xml` signed with `SPARKLE_PRIVATE_KEY`, with download URLs under `releases/download/v{ver}/`.
5. Creates the GitHub Release (published immediately, with generated notes) and uploads the DMGs, appcast and CLI zip.
6. Prints the cask version and sha256.
7. Deletes the temporary keychain.

Then:
- Copy the printed sha256 into `homebrew-tap/Casks/sweepkey.rb` with the new `version`, commit, push. (Automatic cask updates are planned for v1.1.)
- Edit the release notes on GitHub if needed.

`gh release create` publishes at once, so the primary button serves the new DMG as soon as the job ends. To stage instead, add `--draft` to the workflow and publish manually after the checks below.

### 10. Verify the published release
```sh
curl -sIL https://github.com/thisisprabhat/sweepkey/releases/download/v{ver}/Sweepkey-{ver}.dmg | grep -iE '^(HTTP|location|content-length)'
#   302 to the CDN, then 200 with the DMG's length
curl -sIL https://github.com/thisisprabhat/sweepkey/releases/latest/download/appcast.xml | head -1
```
GitHub serves release assets as `application/octet-stream`, which browsers download correctly. The `application/x-apple-diskimage` type applies to the mirror only.

Download the latest URL and compare: `shasum -a 256 Sweepkey.dmg` must equal the printed sha256.

### 11. Sync the mirror and redeploy the site
```sh
cd site
npm run sync-release            # node scripts/sync-release.mjs
npm run build && docker build -t sweepkey-site . && <deploy>
```
Do this right after every release. Until the site is redeployed, the primary button already serves the new DMG while the page still shows the previous version, size and checksum.

## `site/scripts/sync-release.mjs`
A Node script (no dependencies beyond Node ≥ 20 built-ins) run on a Mac, because it calls `spctl` and `xcrun`.

**Input:** the release folder, `CLEANER_DIST` env var or `--from <dir>`, default `../../../utils/cleaner/build/release/dist` relative to `site/`. Optional `--version <ver>`; otherwise the single `Sweepkey-<ver>.dmg` in the folder (more than one → error, asking for `--version`). Alternatively, `--download` fetches `Sweepkey-<ver>.dmg` from the GitHub release into a temp folder, so the mirror can be synced on a machine without a local build.

**Steps:**
1. **Gate.** Run `spctl -a -t open --context context:primary-signature -v <dmg>`. Require exit code 0 **and** `source=Notarized Developer ID` in the output. Then run `xcrun stapler validate <dmg>`. If either fails: print the tool output, write nothing, exit 1.
2. **Measure.** Stream the file through SHA-256 (`crypto.createHash('sha256')`); read the byte size.
3. **Cross-check GitHub (when online).** Fetch `https://api.github.com/repos/thisisprabhat/sweepkey/releases/tags/v<ver>`; find the `Sweepkey-<ver>.dmg` and `Sweepkey.dmg` assets. Their `size` must equal the local size, and their `digest` (`sha256:…`, when the API provides it) must equal the local hash. A mismatch exits 1. Offline: warn and continue.
4. **Copy.** Copy to `public/downloads/Sweepkey-<ver>.dmg` (write to a temp name, then rename). Remove older `Sweepkey-*.dmg` files from `public/downloads/`, keeping only the current version.
5. **Write `src/data/release.json`:**
   ```json
   {
     "version": "0.1.0",
     "tag": "v0.1.0",
     "date": "<YYYY-MM-DD>",
     "minimumOS": "macOS 26",
     "dmg": {
       "fileName": "Sweepkey-0.1.0.dmg",
       "sizeBytes": 0,
       "sizeLabel": "0 MB",
       "sha256": "<64 hex chars>"
     },
     "urls": {
       "latest": "https://github.com/thisisprabhat/sweepkey/releases/download/v{ver}/Sweepkey-{ver}.dmg",
       "versioned": "https://github.com/thisisprabhat/sweepkey/releases/download/v0.1.0/Sweepkey-0.1.0.dmg",
       "mirror": "/downloads/Sweepkey-0.1.0.dmg",
       "cliZip": "https://github.com/thisisprabhat/sweepkey/releases/download/v0.1.0/sweepkey-0.1.0-macos.zip",
       "notes": "https://github.com/thisisprabhat/sweepkey/releases/tag/v0.1.0"
     },
     "notarized": true,
     "syncedAt": "<ISO 8601>"
   }
   ```
   `sizeLabel` uses decimal megabytes (as Finder does), rounded to a whole MB. `date` is the GitHub release's `published_at` (or today, offline).
6. Print a summary: version, size, sha256, mirror path.

**Build-time guard:** `src/data/release.ts` imports `release.json` and throws during `astro build` if it is missing, if `sha256` is not 64 hex characters, or if `public` + `urls.mirror` does not exist.

**Git:** `public/downloads/*.dmg` is in `site/.gitignore` (binaries do not belong in git). `release.json` **is** committed, so the repo records which release the site shows. The Docker build context must include `public/downloads/` (do not list it in `.dockerignore`), so `docker build` must run after the sync on the same machine.

## `site/nginx.conf` (download rules)
Static site, no SPA fallback. Relevant parts:

```nginx
server {
  listen 8080;
  server_name _;
  root /usr/share/nginx/html;
  include /etc/nginx/mime.types;

  sendfile on;
  tcp_nopush on;
  gzip on;
  gzip_types text/css application/javascript application/json image/svg+xml text/plain application/xml;

  # Security headers (repeated in every location that sets its own add_header)
  add_header X-Content-Type-Options nosniff always;
  add_header Referrer-Policy strict-origin-when-cross-origin always;

  # Health check for Docker
  location = /healthz { access_log off; return 200 "ok\n"; }

  # Hashed build assets
  location ^~ /_astro/ {
    add_header Cache-Control "public, max-age=31536000, immutable" always;
    add_header X-Content-Type-Options nosniff always;
    try_files $uri =404;
  }

  # DMG mirror
  location ^~ /downloads/ {
    types {
      application/x-apple-diskimage dmg;
      application/zip              zip;
    }
    default_type application/octet-stream;
    add_header Content-Disposition "attachment" always;
    add_header Cache-Control "public, max-age=31536000, immutable" always;
    add_header X-Content-Type-Options nosniff always;
    add_header X-Robots-Tag "noindex" always;
    try_files $uri =404;          # missing file → real 404, never the home page
  }

  # Pages
  location / {
    add_header Cache-Control "no-cache" always;
    add_header X-Content-Type-Options nosniff always;
    try_files $uri $uri.html $uri/index.html =404;
  }

  error_page 404 /404.html;
}
```
Notes:
- `types { … }` inside the location replaces the MIME map for that location only, so `.dmg` is served as `application/x-apple-diskimage`.
- `immutable` caching is safe because mirror file names are versioned and never overwritten. Never publish a different file under an existing name.
- `add_header` in a location disables inheritance of server-level `add_header`, which is why the security headers are repeated.
- Range requests are on by default for static files, so interrupted downloads can resume.
- `error_page 404 /404.html` returns the styled 404 page with status 404 for unknown pages and missing downloads.
- The container listens on 8080 (for example on `nginxinc/nginx-unprivileged:alpine`, which runs as non-root). TLS terminates at the host's reverse proxy.

**Checks after deploy:**
```sh
curl -sI https://sweepkey.waygosquad.tech/downloads/Sweepkey-{ver}.dmg
#   HTTP/2 200 · content-type: application/x-apple-diskimage · content-disposition: attachment
#   content-length equals release.json sizeBytes
curl -sI https://sweepkey.waygosquad.tech/downloads/Sweepkey-0.0.0.dmg   # → 404
curl -s  https://sweepkey.waygosquad.tech/downloads/Sweepkey-{ver}.dmg | shasum -a 256   # equals release.json sha256
```

## Sparkle appcast
- Feed: `SUFeedURL = $(SPARKLE_FEED_URL)` = `https://github.com/thisisprabhat/sweepkey/releases/latest/download/appcast.xml` (after `configure-repo.sh`). `SUEnableAutomaticChecks` is `true` in `project.yml`.
- The workflow runs `generate_appcast` over a folder containing only the new DMG, signs it with `SPARKLE_PRIVATE_KEY`, sets enclosure URLs to `releases/download/v{ver}/Sweepkey-{ver}.dmg`, and uploads `appcast.xml` to the release. Because the feed URL uses `latest/download`, publishing a release replaces the feed automatically.
- The public key is baked into the app at build time (`SPARKLE_PUBLIC_KEY`). A build without it has the updater disabled and "Check for Updates…" greyed out.
- Sparkle checks are the app's only network use; the site and FAQ say so.
- **Test an update** before announcing a release: install the previous version, publish the new one, choose **Check for Updates…**, confirm it offers, downloads, verifies and relaunches into the new version.
- The site does **not** host the appcast. Keeping it on GitHub means a site outage never breaks updates.

## Runbook for later releases
1. Bump nothing by hand; tag `vX.Y.Z` and push.
2. Wait for the workflow; check the release assets (4 files).
3. Update the Homebrew cask `version` + `sha256`; push the tap.
4. `npm run sync-release` in `site/`, commit `release.json`, build, deploy.
5. Run the "Site" checks above for the download rows.
6. Test the Sparkle update from the previous version.
